# Complete the report verification loop

## What will be built
- Add durable report-analysis and verification fields to community reports, plus one vote per member per report.
- Show an **Analyzing media** state after upload and carry the result into the created report.
- Add **Validate** and **Flag** controls only to active incident-report cards; Level 2 or 3 is required to validate, while signed-in members can flag.
- Calculate each report's trust score from its creator's initial trust, validations, and flags, entirely in the backend.
- Derive and display **Confirmed**, **Disputed**, **Unverified**, or **Expired** consistently on feed cards and report map markers.
- Refresh the affected card and map state after a vote, while keeping ordinary community posts unchanged.

## Security and data rules
- Votes are written through a protected database function, not direct table edits.
- Members cannot vote on their own reports or vote more than once per report.
- The backend independently checks trust level before accepting a validation.
- Report status and score are generated by the backend; clients cannot set them.
- Existing Level 3 restrictions for high-impact incident creation remain unchanged.

## Technical details
- Add a report-vote table with strict row-level access and explicit authenticated/service grants.
- Extend the public and signed-in report queries with safe verification aggregates.
- Keep the current map provider and visual styling; status is conveyed through marker color/title and an active-report summary.
- The media step is a visible simulated analysis workflow, as requested; it will not claim real forensic detection.

## Verification
- Test Level 1 rejection and Level 2/3 validation behavior.
- Test duplicate/self-vote rejection and score/status thresholds.
- Verify media processing, report-card controls, and all four statuses on phone and desktop.
